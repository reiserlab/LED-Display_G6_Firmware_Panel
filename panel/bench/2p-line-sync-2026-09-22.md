# 2P line-sync: why the 22 Sept 2026 Bergamo run leaked display light, and the firmware variant that addresses it

**Date:** 2026-09-22 (analysis of the 22 Sept SNR run; no new bench data yet).
**Inputs:** `Bergamo_testing/092226_SNR/analysis/HANDOVER_300Hz_display_leak.md` (imaging-side
analysis), the flashed firmware on the "older" 2×10 arena (controller `781efe2b`
`feat/mode3-reliability` 2×10 build; 18 × v0.3.1 panels on `g6-panel-v0.3.1-isp-eintlow-9014b5b`),
and a scope photo from a few weeks earlier (line clock + photodiode).
**Result:** both anomalies in the handover are explained by the panel firmware's timing as written,
not by wiring or polarity. A build-flag variant (`pico_v031_eintlow_2p`) is proposed; **untested on
hardware as of this writing**.

## 1. What the scope photo establishes

Agilent capture, Ch2 (2 V/div) = ScanImage line clock, Ch1 (500 mV/div) = photodiode on a panel.

| Measurement | Value | Meaning |
|---|---|---|
| Freq(2) | 15.825 kHz | one clock cycle per imaged line (bidirectional resonant, 7.9 kHz mirror) |
| +Width(2) | 44.825 µs | clock **HIGH while a line is imaged** |
| Duty(2) | 70.9 % | clock **LOW for ≈ 18.4 µs** — the two adjacent 9 µs turnarounds merge into one gap |

Consequences:

- **Polarity is right.** With `EINT_ACTIVE_LOW=1` the panel treats LOW as asserted: Triggered fires a
  row on the HIGH→LOW edge (start of the gap), Gated is lit while LOW (during the gap).
- **The usable dark window is ≈ 18 µs, not 9 µs** as the handover assumed. Whatever a panel row emits
  must start ≈ 1 µs after the falling edge and end before the clock rises again.
- **"Sharp spike, then an extended hump" is binary-code modulation, by design.** A Gray_16 row is four
  bit-planes fired LSB first with durations 1 : 2 : 4 : 8 × `base_T` × duty/255. A pixel whose value
  has bit 1 clear (e.g. 13 = 1101₂, 9 = 1001₂) produces a short plane-0 pulse, a gap, then the long
  plane-2/3 hump. A background of value 15 would show a flat pulse. Nothing is wrong there; what
  matters is that the whole envelope fits inside the LOW gap. In the photo (low duty) it does, with
  ≈ 7 µs to spare.

## 2. Two mechanisms in the panel firmware explain the 22 Sept data

Code: `panel/src/display.cpp` (`Display::update`, `show_row`, `show_gated`), `panel/src/bcm.cpp`,
`panel/src/display_scan_twopio.cpp`; controller `SpiManager.cpp` / `CommandProcessor.cpp`.

### 2a. The gate only schedules a row; it never cuts LED drive (handover H1 confirmed)

`show_row()` hands one row to the two-PIO/DMA scanner as an **autonomous burst** and waits for it to
finish. EINT is sampled before a row starts (Triggered: on the edge; Gated: before each row), never
during one. With the production `base_T = 3 µs`:

| duty_cycle | Gray_16 row on-time | vs 18.4 µs gap (≈ 1 µs latency) |
|---|---|---|
| 25 (≈ DS 10) | ≈ 5 µs | fits |
| 64 (≈ DS 25) | ≈ 12.5 µs | fits |
| 85 | ≈ 17 µs | limit |
| 128 (≈ DS 50) | ≈ 25 µs | overruns ≈ 8 µs into the imaged part of the next line |
| 191 (≈ DS 75) | ≈ 37 µs | overruns ≈ 20 µs |
| 255 (DS 100) | ≈ 50 µs | overruns ≈ 32 µs — lit for most of the imaged line |

That is the pedestal and the edge bands, and the jump between DS 50 (+4 % of flood) and DS 75
(≥ +19 %) is the crossing of the ≈ 17 µs budget. This is not a bug in the trigger path; the BCM base
time was sized for the free-running 1 kHz Persistent scan (20 rows × 50 µs).

### 2b. One-shot Triggered + the controller's 300 Hz re-stream = the 300 Hz envelope (H2, sign corrected)

V1 Triggered (`0x32`) is **one-shot**: 20 EINT edges consume the frame, then `have_pattern_ = false`
and the panel is dark until the next frame arrives. The controller re-transmits the current frame on
every refresh tick — 300 Hz for Gray_16 on the 2×10 build (`constants.h` `refresh_rate_gs16_default`),
whether or not the frame changed. So each panel is lit for 20 line periods (20 × 63.2 µs = **1.26 ms**)
and dark for the remaining **2.07 ms** of every 3.33 ms. The 18 panels receive their blocks staggered
over the ≈ 0.7 ms SPI frame transfer (10 panel sets × ≈ 65 µs at 25 MHz), so the arena-wide light
envelope is a trapezoid ≈ 1.26 + 0.7 ≈ **2.0 ms wide of 3.33 ms ≈ 60 %** — the handover's "smooth
rounded pulse occupying ≈ 60 % of the cycle, dark ≈ 40 %, same shape at every DS". The shape is
DS-independent because it is set by 20 line periods and the transfer time, not by the row on-time.
The refresh PIT is free-running and unrelated to the scanner, hence the 300.03 Hz vs 15 842 Hz beat.

### 2c. Gated or Triggered on 22 Sept?

The data say **Triggered**. Gated (`show_gated`) abandons the scan when EINT deasserts and **restarts
from row 0** on the next assertion. With an 18 µs gate only rows 0…k light (k = ⌊18 µs / row time⌋: one
row at DS 50–100, up to four at DS 10) and there is no deep 300 Hz modulation, only a ≈ 3 % dip at
each frame dequeue. A one-row-per-line burst in the scope photo is also Triggered behaviour. The Studio
run log records the `02 1B 0x` command sent at connect; check it to close the question.

Gated as implemented is unsuitable for line-rate gating regardless of the fix below.

## 3. Firmware variant: `pico_v031_eintlow_2p` (and `pico_v021_eintlow_2p`)

Two build flags, both default-off so every existing env is unchanged (the rebuilt
`pico_v031_eintlow` image is byte-identical to the published `g6-panel-v0.3.1-eintlow-9014b5b.uf2`,
sha256 `d76b8fde…`).

| Flag | Value in `*_eintlow_2p` | Effect |
|---|---|---|
| `EINT_ACTIVE_LOW` | 1 | as the `eintlow` envs |
| `BCM_BASE_ON_US` | `1.0f` (production 3.0) | duty-255 Gray_16 row ≈ 15.3 µs (15 planes-units + PIO overhead) instead of ≈ 50 µs; every duty fits the 18.4 µs gap with ≈ 1–2 µs margin at 255 |
| `TRIGGERED_WRAP` | 1 | Triggered free-runs: one row per EINT edge, 19 → 0 wrap, row phase kept across re-streamed frames; `update()` returns after every row so a new frame is dequeued between rows |

Effects on the imaging picture, if it behaves as designed:

- Light only inside the line-clock LOW gap at every duty (2a fixed).
- No 300 Hz envelope: the panel emits one row on every line, forever, and a re-streamed frame just swaps
  pixel data (2b fixed). Residual structure: a stationary 20-line period from row content.
- Brightness: at a given duty ≈ ⅓ of production per row, and each row fires once per 63 µs line
  instead of once per 50 µs of the 1 kHz scan — roughly ¼ of production overall. Duty remains the knob.
- **First test recommendation: duty ≤ 220** (≈ 13 µs row) to keep ≈ 3 µs margin until the actual
  trigger→LED latency on this arena is measured (0.87 µs on the prototype, ≈ 2 µs suggested by the photo).

Behaviour changes you must know about before running:

1. **`stopDisplay` no longer darkens the panels.** One-shot Triggered went dark 20 edges after the last
   frame; wrap mode holds the last frame and keeps emitting one row per line. Use `allOff` (a dark
   frame) to blank. The protocol below does.
2. **The panels are dark whenever the line clock is absent**, i.e. outside ScanImage acquisition. That
   was already true for one-shot Triggered. For a visual check without imaging, switch the controller to
   panel display mode 1 (Persistent) — that light is ungated.
3. **Each dequeued frame costs one to two line edges.** `precompute_bcm_data` (≈ 100–150 µs, estimate)
   runs with EINT unobserved; at 300 Hz that is ≈ 2 of 53 lines dark per refresh and a slow drift of the
   row↔line phase. **Do not run a Gray_2 pattern at the controller's 1000 Hz GS2 default** (≈ 15 % of
   lines lost) — use Gray_16 patterns or `SET_REFRESH_RATE` ≤ 300.
4. **Error glyphs are ungated.** A `PEnn` glyph is shown Persistent-style (1 kHz, ignores EINT) for the
   error window — ≥ 0.5 s of light in the imaged region. Unchanged by this variant.
5. A panel that never received a Triggered frame shows the boot pattern (Persistent, ungated) until the
   first frame arrives — also unchanged.

Build and package:

```bash
pixi run platformio run -d panel -e pico_v031_eintlow_2p
python panel/tools/build_release.py --only g6-panel-v0.3.1-eintlow-2p   # → dist/*.uf2 + ISP *.bin
```

Deploy through the controller as before (`0xE0` stage → `0xC8` program → `0xC9` verify; the Arena
Studio flasher does this per panel) or by USB/BOOTSEL with the `.uf2`. Roll back with the
`g6-panel-v0.3.1-isp-eintlow-9014b5b.bin` already in `webDisplayTools/flasher/firmware/`.

## 4. Controller-side facts checked

- The controller never sees the line clock. DIO port 2 (`in_trigger`) sets U3 to B→A so BNC J4 drives
  the panels' EINT net through R216 and the fanout; J30 shunt required. Nothing on the Teensy gates
  LED drive or times anything to EINT.
- Refresh: `SET_REFRESH_RATE` (0x16) overrides the 300 Hz / 1000 Hz defaults; Mode 2 frame advance
  (`frame_rate`) is independent of the refresh tick (advance ≤ refresh).
- `SET_PANEL_DISPLAY_MODE` (0x1B) is sticky and applied to every transmitted frame including `ALL_ON`
  / `ALL_OFF`, so `allOff` in Triggered mode is a dark Triggered frame — which is what blanks the
  free-running variant.
- `out_debug_framescan` (DIO role 3) drives a DIO BNC HIGH from the first panel set's CS assert to the
  last panel set's CS release of every frame transfer (`SpiManager::transferFrame`). That is the
  display frame-sync signal to record; port 1 (BNC J3) is free for it.

## 5. The better test (tomorrow)

Protocol: `webDisplayTools/protocols/g6_2x10_2p_duty_sweep.yaml` (validated with the repo linter;
≈ 56 s: 4 s dark, duty 25 / 64 / 128 / 191 / 255 (≈ 10–100 %) rotating at 8 s each, an 8 s static
frame at duty 128, 4 s dark). On `eintlow_2p` every step fits the gap, so the sweep maps usable
brightness end to end with 255 as the margin case; on `9014b5b` the steps above ~85 are the overrun.
Its header lists the Studio steps; in wire terms, once per connection:

| Step | Studio | Wire |
|---|---|---|
| panel display mode Triggered | Controller ▾ → panel mode 2 | `02 1B 02` |
| DIO 1 = frame-transfer envelope | rig io / Controller ▾ (io_ext) | `03 AC 01 03` |
| refresh 300 Hz (GS16 default) | Debug ▾ (unlock) | `03 16 2C 01` |
| telemetry ring on | default | `02 A8 01` |

Record in ScanImage (vDAQ) alongside Ch2/Ch3:

| Signal | Source | Why |
|---|---|---|
| Frame-transfer envelope | controller DIO 1 (BNC J3), 5 V TTL | when each 300 Hz re-stream happened; width = SPI time (≈ 0.7 ms) |
| Line clock loop-back | the same line clock you feed to J4 | phase reference: row fires ≈ 1 µs after each falling edge |
| Condition marker | controller AO (BNC J27) | 0 / 0.5 / 1.0 / 1.5 / 2.0 / 2.5 / 3.0 / 0 V, one level per condition, set by the protocol |
| Photodiode (if available) | on one panel, AI | direct row-envelope vs gap measurement; the Ch3 leak is the *effect*, not the sync |

Ch3 is the leak channel you are quantifying, not a sync; with these three lines every epoch and every
refresh tick is in the recording, and the folded-waveform analysis can be redone against the line
clock rather than a fitted 300.03 Hz. Run the same protocol once on the `9014b5b` eintlow firmware and
once on `eintlow_2p`: the prediction is that the pedestal, the edge bands beyond the SiPM recovery
tail, and the 300 Hz line all collapse on `eintlow_2p` at every duty, with any residual appearing only
at duty 255 (margin) as an edge-column effect.

Controls from the handover that remain worth 20 s each: light path blocked at duty 128 (electrical
pickup, H4); J4 cable pulled at duty 128 on `eintlow_2p` (panels should go **dark**, not flood —
pull-up on EINT; on `9014b5b` one-shot Triggered they also go dark).

## 6. Does telemetry give us what this experiment needs?

Controller ring (`Telemetry.h`, drained by the Studio at 10 Hz into the run log as `cc`/`cf`/`cs` rows
when 0xCB flags bit 2 is set — `781efe2b` has flags 124, so yes):

| Record | What it carries | Useful here |
|---|---|---|
| CMD | receive time, opcode, reply status, **first 8 request bytes** | timestamps every `trialParams`, `0x1B`, `0x16`, `0xAC`, `0xA0` |
| FRAME | SPI-push start time, frame index, pattern id, SD load µs, SPI µs; **only when index or pattern changes** | rotating steps: one record per frame advance (20/s); static step: none after the first |
| STATE | boot, state changes, error glyphs, slow SD, timer fail | error glyphs = ungated-light episodes; correlate with the imaging |

Gaps that matter for this experiment:

1. **The duty byte is not in the CMD record.** `trialParams` is 12 param bytes; the ring keeps 8 (mode,
   pattern, rate, init_pos, half of gain). The Studio run log's `arena_command` echo has the full hex,
   so the duty per condition is recoverable from the run log, not from the ring. Firmware follow-up:
   widen `kCmdPayloadMax` to 12, or add duty to the FRAME record.
2. **Nothing counts EINT edges.** The controller has no edge counter on the trigger route (D35 is a
   translator pass-through in `in_trigger`), and the panel exposes nothing over SPI (CIPO confirmation
   is 3 bytes). Whether the panels actually saw 15.8 kHz edges must come from the loop-back channel
   in ScanImage, or from a `*_spidiag` panel on USB. Follow-up: an edge counter on D35 in
   `in_trigger` role surfaced in GET_HEALTH / a STATE record.
3. The ring overwrites oldest after ≈ 8 s of 300 Hz FRAME traffic; it is only complete if the Studio was
   draining during the run (default on). Confirm `cf` rows exist in today's run log before relying on it.
4. Frames re-streamed with no change produce no FRAME record — by design — so the 300 Hz tick times
   come from the DIO 1 envelope, not from telemetry.

## 8. Review record

`.codex-review/report-20260922-2340.md` (not committed). No blocking findings. Applied from it:
wrap-mode edge-wait bound 100 ms → **1 ms** (a longer bound let the 5-deep display queue fill and
drop while the scanner was idle, so the first frame after restart could be ~100 ms stale); stale
Triggered comments updated; untagged variant builds now carry `<variant>-<sha8>` in the ISP footer
so `GET_FIRMWARE_INFO` / the verify sweep name the variant per panel. Left open: making line-sync an
explicit protocol mode with a controller capability bit instead of a build flag; a USB product suffix;
a host-testable shim for the Triggered state machine.
